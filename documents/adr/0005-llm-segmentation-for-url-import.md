# 0005. URL からの取り込みの本文だけは、Worker の中で Workers AI に区切らせる

## Status
Accepted

## Context
- BudouX は品詞を持たないため、後処理 (ADR 0003 の 2026-10-05 の追記、#31) を足しても、RSVP で 1 回に出して読みやすい塊 (文節〜短い句) の品質に上限がある。issue #32 を起票した時の Wikipedia「ニンニク」の段落の実測は、86 単位のうち 2 文字以下が 18 だった
- bannzai は「ブラウザ内部完結にはこだわりない。AI を使ってもよい」(2026-10-05) と言い、LLM の提供元を Cloudflare Workers AI に決めた (issue #32 の「決めたこと」)
- 形態素解析 (kuromoji.js・Sudachi の WASM 版) を Worker に置く案は、辞書が gzip で 17.8 MB〜50 MB 超 (ADR 0003 の表) で、Workers のスクリプトの大きさとメモリの上限 (https://developers.cloudflare.com/workers/platform/limits/ ) に収まらないため採らない
- URL からの取り込みの本文は、誰でも見られる公開ページの本文で、既に Worker (ADR 0004) を通っている。ここに限れば、ユーザーが貼り付けた本文・ファイルの本文を外に出さずに LLM の区切りを試せる

## Decision
- `/extract` は、取り出した本文の段落 (空行で区切った単位) のうち仮名・漢字を含む段落を、段落ごとに並列で Workers AI (`wrangler.toml` の `[ai]` の binding) のテキスト生成モデルに区切らせ、段落ごとの区切りの位置を `units` (`(number[] | null)[]`) として応答に足す。モデル・プロンプト・上限は `worker/src/segment.ts` を正とする
- 本文の改変 (要約・言い換え・脱落) をさせないため、区切った単位を連結した文字列が元の段落と一致しない応答は捨て、その段落は `null` にする。フロントは `null` の段落と、Worker の段落と文字列が一致しない段落 (先頭に足したタイトル等) を従来どおり BudouX と後処理で分ける
- 1 記事あたりの段落数・1 段落の文字数・文字数の合計と、問い合わせ全体の時間に上限を置き、超えた段落は `null` にする。LLM の呼び出しが失敗しても本文の取り込み自体は失敗にしない
- 区切らせる記事の数を、同じ IP (IPv6 は /64 にまとめる) からの 1 分あたりの件数と、全体の 1 分あたりの件数の両方で制限する (取り込みの回数の制限とは別の Rate Limiting binding。件数は `worker/wrangler.toml`)。超えた記事と、Rate Limiting binding が失敗した記事は区切らせず、全段落を `null` にする
- 区切らずに返した (上限を超える長さの単位を含む) 応答と、読点・閉じ括弧で始まる単位を含む応答も捨てて `null` にする
- 取り込みの画面の説明に、URL から読む時は取り出したページの本文が Workers AI へ渡ることを書く
- フロントは区切りの位置を使う段落でも、文末と空白では従来どおり分け (単位が文をまたがず、日本語の文の中の英単語を 1 語ずつにする)、間は句読点・文末・段落の終わりだけから決める (ADR 0002)
- Worker は本文・LLM の応答を保存・記録しない (ADR 0004 の Workers Logs の無効化をそのまま使い、`console.log` を書かない)
- フロントは区切りの位置 (数値の配列) だけを、本文の SHA-256 をキーに localStorage に保存し、同じ本文を開き直した時は保存した区切りを使う (LLM の区切りは呼ぶたびに変わりうるため、単位の数で照合する読書位置 (`ReadingPosition.unitCount`) を保つ)。本文の文字列は保存しない
- 本文を LLM に送るのは URL からの取り込みだけにする。貼り付け・ファイルの本文は従来どおりブラウザから出さない。広げるかは、配信後にニンニクの段落で BudouX (後処理あり) と LLM の単位を比べてから別に決める

## Consequences
- 不変条件「読み込んだ本文をサーバー・外部サービスへ送らない」の例外 (ADR 0004) が、URL の先の公開ページの本文を Cloudflare Workers AI のモデルに渡すところまで広がる。プライバシーポリシーの「URL からの取り込み」と委託先の表に書く
- Worker の配信 (ユーザー作業 #12 の Secrets 登録) までは LLM を呼べないため、モデルは暫定 (`worker/src/segment.ts` の `segmentationModel`)。配信後に、ニンニクの段落で BudouX (後処理あり) と LLM の単位の一覧を比べて issue #32 のコメントに書き、区切りの品質と速度でモデルを決め直す
- Workers AI のテキスト生成の回数の上限は、アカウント・モデルごとに 1 分あたり 300 回 (https://developers.cloudflare.com/workers-ai/platform/limits/ )。1 記事で最大 30 回呼び、区切らせる記事は全体で 1 分に 3 件 (90 回) までに抑える。`Promise.race` で時間の上限を過ぎた呼び出しは応答を待たないだけで、呼び出し自体は止まらず回数・課金に数えられる
- 費用の見積もり (2026-10-05 の `@cf/google/gemma-4-26b-a4b-it` の料金、入力 100 万トークンあたり $0.10・出力 $0.30。日本語は 1 文字 1 トークン前後とみなす): 上限いっぱいの記事 (20,000 文字) は入力約 2.7 万・出力約 3 万トークンで 1 件約 $0.012。全体の上限 (1 分 3 件) で 1 日休まず区切らせ続けても約 4,300 件・約 $51 で、Wikipedia の数千文字の記事なら 1 件 $0.003 前後
- Rate Limiting binding の回数は Cloudflare のロケーションごとに数えられ、厳密ではない (https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/ )。複数のロケーションから呼ばれると、全体の上限はロケーションの数だけ緩くなる。厳密な費用の上限が要る時は、アカウント側の費用の上限の設定か AI Gateway を使う別の決定にする無料枠を超えた分は Workers の課金に入る
- 同じ記事を取り込み直すと、フロントが保存した区切りを使う場合でも、Worker は LLM に問い合わせ直す (フロントは Worker の応答を受け取るまで本文を知らず、問い合わせを省けない)
- `/extract` の応答の時間が LLM の分 (最大 10 秒) 延びるため、フロントの待ち時間の上限を 20 秒から 30 秒にする
